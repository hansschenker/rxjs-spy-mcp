rxjs-spy-mcp — the workflow, visualized

Three views of the same system: what the pieces are (architecture), what a debugging session looks like (sequence), and what one subscription goes through (lifecycle).

  • create() patches subscribe, so the spy sees every subscription — tag() only adds names.
  • All state lives in the page: records (with the graph), and a ring buffer of log entries.
  • The single JSON surface feeds all three consumers; nothing is console-scraping.

  • The developer never types spy commands — the request is plain language in chat.
  • The agent pulls values by polling logs({ sinceIndex }); the ring buffer means nothing is lost between polls.
  • The answer lands in the chat: the page holds the evidence, the conversation is where debugging happens.

3 · One subscription's lifecycle: S N* (C|E)? U

stateDiagram-v2 [*] --> Active: S subscribe Active --> Active: N next - latest values kept Active --> Completed: C complete Active --> Errored: E error Active --> TornDown: U unsubscribe - cancelled Completed --> TornDown: U automatic teardown Errored --> TornDown: U automatic teardown TornDown --> [*]: flushed after keptDuration note right of Active An S without its U is a live subscription - or a leak. lifecycles() finds these. end note
  • Every trace follows one grammar: S N… C U (completed), S N… E U (errored), or S N… U (cancelled).
  • U always closes the lifecycle — the spy emits it even after C/E, so leak-checking is mechanical.
  • E followed by a fresh S on the same tag is a retry() resubscribing.
